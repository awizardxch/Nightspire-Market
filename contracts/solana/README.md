# xcm_htlc — Nightspire Solana HTLC Escrow

Solana program implementing the HTLC escrow leg of the Nightspire cross-chain
marketplace (SPEC.md §5b). Local-only development against `solana-test-validator`.

## Instructions

### `initialize`
Locks funds into a new HTLC escrow.

| Arg | Type | Description |
|-----|------|-------------|
| `receiver` | Pubkey | **Explicit** claim destination (§5). |
| `refund_addr` | Pubkey | **Explicit** refund destination. Never inferred from sender. |
| `hashlock` | `[u8; 32]` | `sha256(secret)`; secret generated by maker per fill. |
| `timelock` | i64 | Unix timestamp. First-locked leg gets the LONGER timelock (§9). |
| `mint` | `Option<Pubkey>` | `None` = native SOL, `Some` = SPL token escrow. |
| `amount` | u64 | Escrowed amount (lamports / base units). Must be > 0. |
| `fill_id` | `[u8; 32]` | `sha256(offerId \|\| fillNonce)`; bound into PDA seeds. |
| `arbiter` | `Option<Pubkey>` | Opt-in **MEDIATED** arbitration key. `None` = pure HTLC. |
| `exclusive_claimer` | `Option<Pubkey>` | Auction winner (§8). |
| `exclusive_until` | i64 | While `exclusive_until > now`, only `exclusive_claimer` may withdraw. |

**PDA seeds:** `["htlc", fill_id, hashlock]` (exact).

For SPL fills, the caller pre-creates the escrow vault token account
(authority = escrow PDA) before this instruction; the handler validates
mint/authority/zero-balance.

### `withdraw(preimage: [u8; 32])`
Claim branch. Requires:
- `sha256(preimage) == hashlock`
- `now < timelock`
- If exclusive window active: caller must be `exclusive_claimer`

Pays full `amount` to `receiver`. Anyone may submit (payout is hardcoded).

### `refund()`
Timelock branch. Requires `now >= timelock`. Anyone may call.
Pays full `amount` to the **explicit** `refund_addr` — never infers a sender.

### `arbitrate(recipients, amounts)`
**MEDIATED** arbitration branch. Requires:
- `arbiter` was set at lock time (`None` = branch disabled)
- A native **Ed25519Program signature-verification instruction immediately
  preceding** this instruction in the same transaction, carrying the arbiter's
  signature over the exact message
- `sum(amounts) == amount` (exact; no fee skim — §13)
- `recipients.len() == amounts.len()` and non-empty

**Signed message:** `"XCM-ARBITRATE-v1" || escrow_pda || recipients || amounts(u64 LE)`

**Authorization mechanism:** the client prepends an `Ed25519Program`
instruction (e.g. `Ed25519Program.createInstructionWithPublicKey`) signed by
the arbiter over the message above. The Solana runtime cryptographically
verifies the signature when executing the precompile; the program then
inspects that instruction through the instructions sysvar and requires
program-id == Ed25519Program, exactly one signature, signer pubkey ==
escrow `arbiter`, message == expected message, and all bytes inline in the
precompile instruction. The program performs **no curve math itself** —
direct in-program ed25519 verification exceeds Solana's 4096-byte SBF stack
limit (observed as `curve25519-dalek` stack-offset violations at build time),
so the precompile-introspection design is what makes this branch safe to run
on-chain.

**⚠️ TRUST WARNING:** The arbiter is **unilateral** — a single key can redirect
100% of funds to arbitrary recipients. This is MEDIATED arbitration, not
trustless. Use only with a mutually-trusted arbiter. An independent audit is
**required** before mainnet deployment.

## Design Notes

### Native SOL transfers
The escrow PDA is program-owned (has data), so `system_instruction::transfer`
cannot be used (System Program only transfers from system-owned accounts).
All SOL movements use **direct lamport mutation** by the owning program:
subtract from escrow, add to destination. Rent is preserved for Anchor's
`close` constraint, which reclaims it to the branch's primary destination.

### Arbiter verification
Authorization is proven by a native Ed25519Program precompile instruction
placed immediately before the `arbitrate` instruction in the same transaction
(the client builds it with `Ed25519Program.createInstructionWithPublicKey`).
The runtime verifies the cryptographic signature; the program inspects the
precompile instruction via the instructions sysvar and binds (program id,
signer pubkey, exact message). No `ed25519-dalek` dependency — direct
in-program curve verification exceeds the 4096-byte SBF stack limit.

### Rent handling
The escrow data account is closed on every terminal branch via Anchor's
`close` constraint. Reclaimed rent goes to:
- `withdraw` → `receiver`
- `refund` → `refund_addr`
- `arbitrate` → `refund_addr` (documented neutral default)

The SPL vault is closed via `CloseAccount` (authority = escrow PDA) to the
same destination.

## Cross-VM Test Vector

Fixed 32-byte secret for SHA-256 compatibility testing:

- **secret:** `xcm-htlc-vector-v1-32bytes!!!!!!` (UTF-8, exactly 32 bytes)
- **sha256:** `5b9a96bad43ae10d584a4310b79d57d70e1b2f5ab89ea58b20f9f2091f3e463b`
  (ground truth from coreutils `sha256sum`)

The test asserts `node:crypto` matches this, then performs an on-chain
withdraw. Success proves Solana's `hash::hash` is byte-identical to the EVM
`sha256` precompile and Chia's `sha256` operator.

## Build

### Prerequisites
- Rust (1.79+; the Agave SBF platform tools work with the Rust they ship)
- Agave/Solana CLI 2.2.x providing `cargo-build-sbf`
- Anchor CLI 0.31.2 (optional — only needed to regenerate the IDL)

Install all three per the official Solana/Agave/Anchor docs; any standard
install location works. (The original development sandbox used a local
crates-index mirror because of restricted network egress; that workaround is
sandbox-specific and is intentionally NOT part of this repo.)

### Vendored crates
- `solana-native-token 2.2.1`, `spl-token 7.0.0` — .crate unreachable from sandbox
- `blake3 1.8.7` — `traits-preview` feature neutered (it pulls `digest 0.11` →
  `hybrid-array`, which needs Rust 1.85). `solana-program` enables the feature
  but never uses the `traits` module.

### Build command
```bash
cargo build-sbf
# Output: target/sbpf-solana-solana/release/xcm_htlc.so
```

Note: `anchor build` requires the `idl-build` feature, which needs `regex`
(not in the local mirror). The IDL at `target/idl/xcm_htlc.json` is
hand-maintained from the program interface: instruction/account
discriminators are the deterministic `sha256("global:<name>")` /
`sha256("account:<name>")` values (verified against the spec — the earlier
manual draft had wrong discriminators for `refund`, `arbitrate`, and
`HtlcEscrow`, now corrected). TypeScript types generated via
`anchor idl type`. The IDL remains **unverified until `idl-build` can run** —
re-enable the feature, mirror its dependencies, and regenerate before
treating it as authoritative.

## Tests

`tests/xcm_htlc.ts` covers (12 test cases):
1. Native SOL happy path (initialize → withdraw)
2. SPL happy path with local mint
3. Third-party refund after timelock
4. Wrong preimage rejection
5. Withdraw after timelock rejection
6. Refund before timelock rejection
7. Exclusive-claimer enforcement (reject non-winner, allow after window)
8. Valid arbiter-signature split
9. `arbiter=None` rejection
10. Wrong arbiter signer rejection
11. PDA determinism (`["htlc", fill_id, hashlock]`)
12. Cross-VM SHA-256 compatibility

Run against local validator:
```bash
solana-test-validator --reset
solana program deploy target/deploy/xcm_htlc.so --program-id target/deploy/xcm_htlc-keypair.json
anchor test --skip-local-validator
```

## Security Notes

- **Independent audit required before mainnet.** This code has not been audited.
- Arbitration is **MEDIATED and unilateral** — the arbiter key is a single
  point of trust. Document this to users.
- No protocol fee skim (§13) — `arbitrate` requires exact-sum payouts.
- Refund address is explicit (§5) — the program never infers a sender.
- Timelocks use testnet durations (§9); verify mainnet parameters separately.
